# 团队协作工作流（Joey + Teresa）

> 原则：**一个 GitHub 仓库存所有东西，两人分目录写代码，接口先定好，每 1–2 小时合并一次。**
> 黑客松只有 24 小时，不搞复杂流程，只做能防止「互相覆盖、最后合不上、密钥泄露」的最少规则。

---

## 1. 一次性准备（开赛前 15 分钟做完）

| 步骤 | 谁做 | 怎么做 |
|---|---|---|
| 建私有 GitHub 仓库并推送 | Joey | 本文件夹就是仓库，`gh repo create` 推上去 |
| 邀请 Teresa 当协作者 | Joey | `gh repo edit` / 网页 Settings → Collaborators |
| 克隆仓库 | Teresa | `git clone <仓库地址>`，存在自己电脑上 |
| 配 Gemini API Key | 两人 | 复制 `.env.example` 为 `.env`，填 key（**key 只通过私信发，不进 git**）|
| 装好 AI 编程工具 | 两人 | Claude Code / Cursor 打开仓库，会自动读 `CLAUDE.md` |
| 建沟通群 | 两人 | 微信 / iMessage 一个群，发链接、key、截图都用这个 |

> Joey 的仓库在 SanDisk SSD（exFAT 格式）上。`.gitignore` 已经排除了 macOS 生成的 `._*` 文件，也设置了 `core.fileMode=false`，避免出现假的「文件改动」。

---

## 2. 分工 = 分目录（最重要，能避免 90% 的冲突）

| 目录 | 负责人 | 内容 |
|---|---|---|
| `backend/` | **A**（后端 / AI） | API 服务、Gemini 调用、prompt、数据库 |
| `frontend/` | **B**（前端 / 产品） | 页面、交互、调用后端 |
| `docs/API.md` | **两人一起定，A 负责维护** | 前后端接口约定 |
| `docs/TASKS.md` | 两人 | 任务板 |
| `pitch/`、`assets/` | **B** | PPT、讲稿、截图、demo 视频 |

**规则：不要改对方目录下的文件。** 真要改，先在群里说一声。

谁做 A、谁做 B，等点子定了再确定，写在 `docs/TASKS.md` 最上面。

---

## 3. 接口先行（第 1 小时内完成）

1. 点子定了以后，两人花 20 分钟在 `docs/API.md` 里写好每个接口：路径、请求 JSON、返回 JSON，每个都给一个例子。
2. B 按例子 JSON **写 mock 数据**，马上开始做前端，不用等后端。
3. A 按约定实现接口。
4. 接口要改，**先改 `API.md`，提交，在群里 @ 对方**，再去改代码。

---

## 4. Git 流程（简化版）

```
main  ← 随时能跑、能 demo 的版本
 ├── joey/xxx     ← Joey 的功能分支
 └── teresa/xxx   ← Teresa 的功能分支
```

**日常循环（每做完一小块就跑一遍）：**
```bash
git switch -c joey/gemini-chat        # 开一个新功能分支（名字：人名/功能）
# ...写代码...
git add -A && git commit -m "feat: gemini chat endpoint"
git fetch origin && git rebase origin/main   # 先把对方的新代码同步过来
git push -u origin HEAD
gh pr create --fill && gh pr merge --squash --delete-branch   # 合进 main
git switch main && git pull
```

- **每 1–2 小时至少合进 main 一次**，不要攒到最后才合。
- 合进 main 之前，自己本地要能跑起来。
- 遇到冲突：在群里喊一声，两人一起看（或者交给 Claude Code 解决），**不要直接 force push**。
- 提交信息前缀：`feat:` 新功能 / `fix:` 修 bug / `docs:` 文档 / `chore:` 杂项。
- **第 18 小时以后（约周日 8 AM）冻结 main**：只合 bug 修复。

## 5. 任务板：Google Doc（共享文档）

**链接：** https://docs.google.com/document/d/1zOFvMK21tq3OHowYNdMt2NikQcE9c1DU3L-RKZY8VN4/edit

所有任务分工、站会记录、待确认问题都写在这个 Google Doc 里。`docs/TASKS.md` 不再更新。

### 填写规则

- 三栏：**待做 / 进行中 / 完成**，每条任务写上负责人：`- [ ] [Joey] 实现 /api/analyze`
- 开始做某条任务时就把它挪到「进行中」，这样对方知道你在做什么，不会重复。
- 每次同步都过一遍任务板，砍掉做不完的任务。
- 用 AI 工具时可以直接说：「读 `docs/TASKS.md`，帮我做第 X 条」。

---

## 6. 和 AI 一起写代码（Claude Code / Cursor）

- 仓库根目录的 `CLAUDE.md` 是给 AI 的「项目说明书」：做什么项目、技术栈、目录归属、规则。**两人的 AI 读的是同一份**，写出来的风格才一致。
- 点子和技术栈定了以后，**第一时间更新 `CLAUDE.md`**。
- 让 AI 只改自己负责的目录。提示词里加一句：「只修改 `backend/`」。
- AI 写的代码要在本地跑一遍再提交。
- Gemini 的 prompt 统一放在 `backend/prompts/`，方便两人一起调。

## 7. 同步节奏

| 时间（约） | 做什么 |
|---|---|
| 开赛 | 一起想点子 → 定点子 → 写 `API.md` 和 `TASKS.md` |
| 每 3 小时 | **5 分钟站会**：完成了什么 / 卡在哪 / 下一步，然后更新任务板 |
| 第 8 小时 | 中期检查：主流程能不能从头点到尾？不能就砍功能 |
| 夜里 | 轮流睡 2–3 小时，睡前把代码 push 上去，在群里说一下进度 |
| **周日 ~8 AM** | 冻结功能 |
| **周日 10 AM 前** | 交 Devpost 草稿（B 负责） |
| **周日 12 PM 前** | 交最终版本（要留出至少 30 分钟余量） |

---

## 8. 密钥和安全
- `.env` 已经写进 `.gitignore`，**永远不要提交它**。提交前跑一下 `git status`，确认里面没有 `.env`。
- 前端代码里不要直接写 Gemini key，前端统一通过后端去调用 Gemini。
- 如果 key 不小心提交了：马上去 Google AI Studio 删掉这个 key、换一个新的，再告诉对方。
